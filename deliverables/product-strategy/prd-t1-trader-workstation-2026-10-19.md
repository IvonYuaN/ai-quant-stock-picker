## TL;DR

1. **中心对象换人**：首页从"今日推荐榜"改为"**今日提醒收件箱**"——从"今天有什么票"变成"**我手里这些票今天有什么事**"。这一条决定其余所有改动。
2. **缺的从来不是能力，是接线**。卖出阈值（L1/L2/L4/L5）**全部现成**，只是接在回测上没接实盘持仓；候选冻结的 save/load_snapshot 也现成，只差一个当日冻结闸门。**P0 八条中 6 条为接线**，1 条轻 UI，1 条新写（炸板钩子）。
3. **一个新增的 P0 是排序，不是导航**：`/today` 候选区只按策略分组（动量/均线…），**没有"命中我的持仓/自选"的优先级**。用户优先级 ②（选股+大盘→买卖建议）的卡点在这里——候选列表再准，排在动量股后面也等于没用。
4. **为什么可以大刀阔斧地砍**：后端 63 个端点，前端只实调 21 个；31 个单票数据端点前端零调用；ConceptsPage / StockResearchPage 是**孤儿路由**（既不在导航也无前端实调）。**弹药早就装好了，只是没上膛**——收敛导航不损失能力，只是不再用零消费的面板冒充功能。

## 一、问题陈述

### 1.1 问题

用户是 A 股 **T+1 实盘短线交易者**，有自己的交易软件，**明确不要本系统下单**。他要的是一个副驾驶：报单、盯盘、到点喊他。

当前系统给的是一个**研究员仪表盘**：每天按固定流程产出 N 批候选 + 一堆量化门禁数字 + 几个零消费的面板。他在能力上不欠，欠的是三根线：

| 断裂 | 用户可感知的症状 | 机制根因（已核实） |
|---|---|---|
| loop ③ 持仓/自选/板块分裂 | "我的东西散在三个地方" | `HoldingsPage` / `WatchlistPage` 两独立页 + `ConceptsPage` 孤儿路由 + 导航 7 项分散 |
| loop ④ 候选日变 | **"早中晚一批新内容"** | `portfolio/snapshot.py` 只做每日留档+跨日对比；`save_snapshot` 每次 `screen_universe`（cli.py:4765/5239）就整批重算重存，**无当日冻结闸门** |
| loop ⑥ 无操作回录 | "我买/卖完，系统不知道" | `backend/portfolio.py` 有 `add_holding`/`close_position`，UI 无顺手入口 |
| loop ⑦ 无卖出提醒 | "该卖没人喊我" | 风控齐全，但**全仓无一处**对实盘持仓跑风控产提醒 |
| **loop ⑤ 候选与持仓无关联**（v2 新增） | **候选列表里看不出哪些是我持仓/自选** | `/today` 候选区**只按策略分组**（动量/均线/…），**无"命中我的持仓/自选"优先级排序** |

### 1.2 为什么现在做

五条断裂里任意一条单独出现都只是"体验不好"；**同时出现 = 用户每天要重新建立一次"这系统今天想说什么"的认知成本**，且无法把任何一条输出归因到自己某个决定上。结果是：投入最多的模块（DSR/PBO/CSCV/7 维权重）零消费，而零消费又进一步印证"这系统是为做而作"。这是一个**信任赤字**，会持续复利。

其中 **loop ⑤ 最隐蔽也最致命**：它让系统输出的"选股结论"和用户真实的"持仓决策"成为**两条互不相交的线**。用户要的是"围绕我持仓的买卖建议"，系统给的是"全市场策略分组排名"——即使两边都对，也拼不成一个决策。

### 1.3 v1 成功的量化边界

不新增选股能力。v1 只承诺：**同一天内用户看到的东西不再无声变化；系统会在该喊的时候喊；候选列表第一眼就能看出哪些命中我的持仓和自选。**

### 1.4 现状盘点：端点利用率（v2 新增，砍与不砍的量化依据）

| 指标 | 数值 | 含义 |
|---|---|---|
| 后端端点总数 | **63** | 系统能力面 |
| 前端实际调用 | **21**（33%） | 真实进入用户视野的 |
| 前端零调用的单票数据端点 | **31** | kline / financials / margin / fund-flow / 龙虎榜 / 解禁 / 涨停 / 热概念 / 投资者问答 … |
| 孤儿路由 | **ConceptsPage、StockResearchPage** | 既不在 `ia.ts` NAV_LINES，前端也零实调 |
| 内容重复 | ConceptsPage 与 `/stream` 概念异动**同源同内容** | 两处入口展示同一份数据 |

**判读（三条结论）**：
1. **31 个单票数据端点是"弹药没上膛"**：不是能力缺失，是**没有消费界面**。它们是研究员数据底座，用户作为实盘交易者不需要逐项查财报/解禁/龙虎榜。→ 保留端点、砍掉入口，不砍能力。
2. **ConceptsPage 砍掉零风险**：孤儿路由 + 内容与 `/stream` 重复。砍它是**去重**，不是减功能。
3. **收敛导航的正确姿态是"合并同类项"而非"关功能"**：持仓+自选合并为一个对象（用户视角的真实需求），笔记/资料砍掉（见 P1-1），`/stock/:code` 改深链（保留能力不占导航位）。

**这个盘点支撑了本文最大胆的建议**：把导航从 7 项收敛到 4 项，**不损失任何用户可消费的能力**，只是不再用零消费面板冒充功能。

## 二、目标用户

### 2.1 主要人群（唯一服务对象）

**P0 人群：T+1 实盘短线交易者（当前唯一用户本人）**
- 每日决策节奏：盘前定计划（看消息+大盘+候选）→ 交易软件下单 → 收盘前处理持仓 → 收盘后复盘
- 关注：持仓 3–10 只，自选 10–30 只
- 判据："今天我该不该动这几只票"，而不是"今天有什么新票"

### 2.2 次要人群

**P1 人群：未来的自用扩展位（不作为 v1 设计输入）**
- 多账户/多策略并行 → v1 数据模型预留 `account` 字段，但**不做多账户 UI**。
- 明确不服务：机构、多用户、协作。系统定位是**单人本地工作台**。

### 2.3 用户故事（T+1 实盘视角，围绕断点）

**US-1（loop ③⑦，对应目标1+2）**
> 作为 T+1 短线交易者，我打开系统的第一眼要是"**我手里这些票今天有什么事**"——哪只触发了止损、哪只炸板了，而不是又一批我不认识的票。
> **Then 我不需要重新读一遍系统今天想说什么。**

**US-2（loop ③，对应目标2）**
> 作为 T+1 短线交易者，我希望持仓和自选在**同一屏**里对照，能按"该卖/该看/该留"排序，而不是在两个页面之间来回切。
> **Then 我 5 秒内能判断今天要处理哪几只。**

**US-3（loop ⑥⑦，对应目标3）**
> 作为 T+1 短线交易者，我在交易软件上买完/卖完后，**顺手**录一行"我买了 XX 100 股 @ 12.3"，系统就自动给我这只票挂上默认卖出阈值（硬止损 −5%、破 MA5、跟踪止损 5%）。
> **Then 我不需要自己研究怎么配预警——社区最常见的误用就是"只设买入预警不设风险预警"。**

**US-4（loop ⑦，对应目标3）**
> 作为 T+1 短线交易者，当 XX 有效跌破 MA5 / 炸板 / 从最高点回撤 5% 时，我要**今天之内**看到一条带触发依据的提醒。
> **Then 我能立刻复核这条提醒的依据是否成立（因为它是确定性阈值、我看得懂），而不是猜模型在想什么。**

**US-5（loop ④，对应目标1的稳定性保障）**
> 作为 T+1 短线交易者，今日候选在**盘前生成后就要冻结**，盘中我再看它，长的是同一批票，只是多了"新增/失效"标注。
> **Then 我开盘前定下的买卖计划，到收盘前都还成立。**

**US-6（loop ⑤，v2 新增，对应目标1+2 的"关联性"）**
> 作为 T+1 短线交易者，我看今日候选时，**第一眼就要看到命中我持仓/自选的那几只**——它们要么顶到最前，要么带一个"持仓""自选"标签，而不是混在动量股/均线股里靠我逐条翻找。
> **Then 候选列表直接回答"今天我要动的那几只，模型怎么看"，而不只是一张全市场排名表。**

## 三、成功指标

| 指标 | 当前 | 目标 | 评估时间 |
|---|---|---|---|
| **日内候选集合稳定性**：同一自然日 3 次进入（早/中/晚）候选列表差异条数 | 每次全量刷新（≈100% 变化） | **0 条差异**（新增/失效以增量角标标注，不替换原列表） | 上线后第 1 周 |

| **首页首屏回答"我手里今天有什么事"**：持仓有触发时是否出现在首屏 | 0 项（无此视图） | 持仓有触发时 **100%** 出现在首屏 | 上线后第 1 周 |

| **卖出提醒有效率**：提醒条目被"已处理/忽略"的比例（衡量是否制造噪音） | — | 首周观测，**噪音率（忽略+未处理）< 40%**；超标则下调默认灵敏度 | 上线后第 2–4 周 |
| **主界面量化指标清零**：`ia.ts` NAV_LINES 中 DSR/PBO/CSCV/7 维权重入口数 | 存在 | **0** | 上线时 |
| **导航项数量**（信息噪音总指标） | **7 项**（2 组） | **4 项**（每日决策 3 + 我的 1） | 上线时 |

**反指标（防止改坏）**：
- 今日提醒非空率若长期 > 80%，说明阈值过敏 → 必须收敛，而不是让用户关掉提醒。
- 每日新增"我的持仓"条目数异常暴涨（>20），说明用户误录 → 需要回录校验。
- **若"命中持仓/自选"候选大量出现在末位**，说明现成候选池与实盘持仓重叠度太低 → 说明筛选口径本身要调（需另开需求），而非 UI 问题。

| **G1 提醒收件箱** | 首页中心对象从"今天有什么票"换成"**我手里这些票今天有什么事**" | 首页信息架构 + 风控告警出口 + **候选排序口径** | ⑦⑤（+④ 稳定化） | P0-1 P0-2 P0-5 |
| **G2 我的仓位持久层** | 持仓 + 自选合并为**唯一持久层**，全系统所有输出都挂在它上面 | 数据组织 + 页面合并 + 候选冻结 | ③④ | P0-4 P0-6 P1-1 |
| **G3 卖出提醒闭环** | 操作回录 → **自动挂默认阈值** → 触发提醒 → 用户处置回写 | 输入通道 + 风控接线 | ⑥⑦ | P0-3 P0-7 P1-3 P1-4 |

**三个目标为什么正交**：G1 改"读什么"（信息架构 + 排序口径）、G2 改"围着谁转"（对象）、G3 改"写什么"（输入 + 告警）。三者在实现上互不依赖、可并行。

> ⚠ **v2 修正（路线图核实后）**：本节初版称"G3 依赖 G2 提供的持仓数据源，故 G2 必须先落地"——**该推论不成立，已删除**。持仓数据源（`backend/portfolio.py::add_holding/close_position` + `/api/portfolio`）**已经存在且正在服务 `HoldingsPage`**，G2 提供的是"持仓+自选合并视图"这个**展示层**产物，不产生任何新数据源。
>
> **真正的硬依赖只有两条**：
> ```
> P0-3（回录入口）──写入──► P0-7（自动挂阈值，挂在提交回调上，缺 P0-3 无法实现）
> P0-2（风控接实盘）──产 alert_event──► P0-1（首页收件箱，无提醒数据则恒空）
> ```
> **真正必须最先落地的是 P0-3**（输入通道），而非 G2。这正是"v1 初版把 P0-3 排进 M2 会导致 M0 空转"的根因，见 4.3 修订说明与第八章。

### 4.2 三个目标的验收标准（Given/When/Then）

**G1 今日提醒收件箱**
- **Given** 用户持仓 5 只，其中 2 只今日触发 L1/L2 阈值；**When** 用户在 09:35 打开系统；**Then** 首屏第一个模块是「今日提醒」，列出这 2 条，每条包含：代码 / 当前价 / **触发层级（L1–L5）** / **触发依据的具体数值**（如"现价 11.62 < 成本 12.20 × 0.95 = 11.59"）/ 建议动作 / 已持仓天数；**且**该模块在无触发时显示"今日无触发"而不是空白。
- **Given** 某条提醒为 MACD 死叉；**When** 用户点击"触发依据"；**Then** 展开该股日线图并高亮死叉位置，用户可自行复核，**不要求信任模型分数**。
- **Given** 同一条件今日已提醒过一次；**When** 同一条件在 14:00 再次满足；**Then** 按提醒频率档位处理（默认"仅提醒一次"，不重复打扰）。
- **Given（v2 新增）** 今日候选共 20 只，其中 2 只在用户持仓、3 只在自选；**When** 用户打开今日选股；**Then** 这 5 只出现在列表**前 5 位**并带「持仓」「自选」标签，其余候选按原策略分组排在其后。

**G2 我的仓位持久层**
- **Given** 用户有 5 只持仓 + 20 只自选；**When** 进入「我的持仓」；**Then** **单页**呈现全部 25 条，按"有触发 > 持仓未触发 > 自选命中今日候选 > 纯自选"分组排序；每条显示所属板块标签（**板块降级为标签，不独立成页**）。
- **Given** 今日候选已盘前冻结；**When** 用户 13:00 再次查看今日候选；**Then** 列表与 09:15 完全一致，仅在新增项上显示"新增"角标、在失效项上显示"已失效"角标，**原列表不重排、不移除**。
- **Given** 用户删除某只自选；**When** 该股同时在今日候选中；**Then** 从"我关注范围内"的候选视图中移除，并在提醒中心留下"1 只自选已移出监控范围"的记录（**输入可控**：用户能看见自己的移除动作产生了后果）。

**G3 卖出提醒闭环**
- **Given** 用户通过「我操作了」新建一笔买入（代码/方向/价格/数量）；**When** 提交成功；**Then** 系统**自动挂载** L1（成本 −5%）、L2（有效跌破 MA5）、L5（跟踪止损，自最高价回撤 5%，只升不降），并将该票标记为"强化盯盘"，提示文案明确告知"已自动为你挂了 3 条卖出提醒，可随时改或关"。
- **Given** 用户未手动回录、仅通过其他路径变更持仓；**When** 持仓成本发生变化；**Then** L1 阈值**跟随成本自动重算**并保留在提醒设置中（避免"回录 = 重配"的隐式负担）。
- **Given** 用户点击提醒上的"我已卖出"；**When** 确认成交价与数量；**Then** 直接复用 `backend/portfolio.py::close_position` 写入，并**关闭该票全部未触发提醒**，在提醒历史中留痕。
- **Given** 用户在提醒上点"忽略"；**When** 同一条件再次触发；**Then** 按频率档位处理，且忽略次数进入该条件的灵敏度自适应（连续忽略 2 次 → 自动降级为"每日一次"并提示用户）。

> 初版（以及初版里程碑）把 P0-3「我操作了」放进 M2，是**实质性缺陷**。缺陷链：

> ⚠ **v3 修正——P0-5 的改造量由"低"上调为"中"**（依据实测代码）：

> ⚠ **成本构成更正**：成本在**置顶分组 + 前 5 位截断 + 与现有 `strategyCounts` 分组的视觉层级协调**，**不在"打通持仓→候选的关联"**（关联已由 `ownedKind()` 具备）。
>
> ✅ **"持仓命中项被沉底"反模式：已核查，不存在**（v3.3 闭环）。此前记录了一项M1 前置待查事项，路线图已复核 `candidate-view.ts:78-97` 排序实现全文：
> ```ts
> const sorted = [...filtered].sort((a, b) => {
>   switch (options.sort) {
>     case "ready":    if (a.ready !== b.ready) return a.ready ? -1 : 1;
>                      return b.score - a.score;
>     case "evidence": if (b.messageCount !== b.messageCount) …; return b.score - a.score;
>     case "score": default: return b.score - a.score;

> 三档 `CandidateSortKey = "score" | "ready" | "evidence"`（`candidate-view.ts:7`），默认 `useState("score")`（`CandidateSection.tsx:474`）⇒ **只按 `ready` / `score` / `messageCount` 排序，持仓与自选维度完全不参与**。
> ⇒ **当前版本没有在做 P0-5 的反面**，该项无需在 M1 开工前再查。
>
> 📌 **对 `hideOwned` 的定位更正**（本 PRD 前一版曾把它列为风险，实为误判）：`hideOwned`（`:477/530`）是 **`exclude` 谓词，只做可见性过滤、不参与排序** ⇒ 它的存在**不意味着持仓项被排到最后**，只意味着"用户可主动把持仓项藏起来"（一个合理功能）。
> **⇒ P0-5 的真正内容因此更清楚：把 `hideOwned` 从"可见性开关"升级为"默认置顶"——底层判定能力共用，差别在呈现层级。**
>
> ⚠ **由此引出的一条真实风险（非"沉底"，而是"无入口"）**：既然三档排序都不看持仓维度，那么**用户今天没有任何排序方式能看到"命中我持仓的排最前"**。P0-5 的必要性不来自"修复反向行为"，而来自**补上一个当前完全不存在的视角**——这不影响其优先级，但**说服理由应当用这个，而不是"当前在反向做"（后者已被证伪）**。

> ⚠ **v3 修正——P0-5 的依赖被高估，此处易被误读**：
> P0-5 只需**持仓/自选数据源（已现成，`/api/portfolio` + 自选数据源）**，**不依赖 P0-6 的页面合并**。P0-6 产出的是"我的持仓"这个**展示层页面**，P0-5 要的是底层数据。**若按"P0-5 依赖 P0-6"排期，会把两个本可并行的低改造需求错误串行化。** P0-5 与 P0-6 同批（均在 M1）仅为开发效率考虑，**非硬依赖**。

> ⚠ **v3 修正——P0-5 与 P0-4 必须相邻交付（重要）**：
> P0-5 上线后会让系统**明确承诺**"命中你持仓的这几只顶到第一位"，但若此时 P0-4 未上线，整批重算会在盘中把它们撤回：
> ```
> 09:15  P0-5 上线 → "命中你持仓"的 2 只顶到第 1、2 位，打上「持仓」标签
>               ↓ 用户据此定下今日计划（这正是 P0-5 的设计目的）
> 11:00  整批重算 → 这 2 只掉出列表，或被陌生票挤下去
> 14:00  再看 → 又是另一批
> ```
> ⇒ **P0-5 无 P0-4 会制造一个 v2 之前不存在的失败模式：系统先明确承诺"这几只是你的票"，然后把它们撤回。** 这比"候选一直是榜单"更伤信任——它从"无承诺"变成了**主动失信**。
> ⇒ **排期硬约束：P0-5（P0-5）与 P0-4（P0-4）必须相邻交付，不可隔着任意里程碑。** 详见 8.6。

导航（收敛后）

| 导航项 | 定位 | 内容 | 相对现状（NAV_LINES 7 项 → 4 项） |
|---|---|---|---|
| **① 今日选股** | **默认落地页（入口 + 状态）** | 顶部置顶「今日提醒」收件箱；候选区**命中持仓/自选优先**、冻结快照 | 现状已存在，新增：提醒模块 + **P0-5 排序** + P0-4 冻结 |
| **② 小道信息** | **输入源（一等导航位）** | 12 赛道 108 源，可信度分层；吸收概念异动 | 现状已存在，新增：吸收 `/concepts` |
| **③ 行情环境** | 环境过滤器（一眼） | 指数/情绪，一句话定性 | 现状已存在，**降级为二级** |

> **为什么今日提醒不单列导航项**：主理人核实的 IA 已收敛为 4 项。G1 的诉求（第一眼看到"我手里的票今天有什么事"）通过**在默认落地页顶部置顶该模块**满足，不额外增加导航层级——这样既拿到提醒的首屏权重，又不让导航从 4 项膨胀到 5 项。若老大认为提醒需要独立入口，见 **Q8**。

#### 4.4.2 消息流定位：置顶 vs 折叠 —— v2 已裁决（Q1 收敛）

主理人核实的 `ia.ts` 导航方案中，**小道信息是一等导航项**（每日决策组第 2 项），既不是"占据首屏"的置顶，也不是"折叠进 tab"。

| | 瑞思（用户视角诊断） | 竞析（竞品对标） | **主理人 IA（本 PRD v2 采用）** |
|---|---|---|---|
| 主张 | 消息流**保留并置顶**（优先级第一位） | 消息流**折叠为提醒中心的一个 tab / 侧栏** | **一级导航项**（每日决策组），占导航位但**不占首屏** |
| 理由 | 用户原话"合理的小道消息"是优先级 ① | 它是**输入源不是状态**，不该与状态并列抢首屏 | 两者之间：**给导航权重（尊重优先级 ①），不给首屏权重（保住 G1）** |
| 风险 | 首屏被占满 → G1 落空 | 优先级 ① 被降级 → 感知"你要收敛我的东西" | 首屏仍是候选榜 → 需靠 P0-1 提醒模块置顶 + P0-5 排序来兑现 G1 |

**裁决结论**：**Q1 由主理人 IA 裁决 —— 消息流保留一级导航位（部分倾向瑞思），但不占据首屏（部分倾向竞析）。**
- 保住优先级 ① 的**消费权**：导航位保留、未读红点保留、概念异动内容并入使其更完整（不降级、不隐藏、不合并权限）。
- 保住 G1 的**首屏权**：首屏第一模块是今日提醒，候选区命中优先。
- **G1 的兑现责任因此落在 P0-1 + P0-5 两件事上**（提醒置顶 + 候选命中优先），这两条不能砍。

#### 4.4.3 主流程：从打开到决策（≤ 90 秒）

```
① 打开系统 → 默认落地「今日选股」
   └→ 首屏第一模块「今日提醒」
        ├ 无触发 → "今日无触发" + 行情环境一句话（30 秒结束）
        └ 有触发 → 逐条复核
              ├ 展开"触发依据"看数值/图（可自行判定）
              ├ 我已卖出 → 回写 close_position + 关闭该票提醒 ⟶ ④
              └ 忽略     → 计入灵敏度自适应（连续 2 次自动降频）
② 往下看候选区（已冻结 + 命中优先）
      └ 命中持仓的排最前 → 命中自选次之 → 其余按策略分组
            └ 计划依然成立（列表不日内变动），且一眼看出"今天动哪几只"
③ 「行情环境」一眼过环境（打板纪律：大盘不能大跌）
④ 「小道信息」消费消息（含概念异动，带可信度分层）
⑤ 「我的持仓」对照全貌
      └ 分组：触发中 > 持仓未触发 > 命中候选自选 > 纯自选
            └ 板块作为行内标签，可点标签过滤
⑥ 盘中去交易软件下单（系统不介入）
⑦ 回来 → 「我的持仓」页内「我操作了」（≤3 点击）
      └ 自动挂 L1/L2/L5 阈值 → 该票进入强化盯盘 ⟶ 回到 ①
```

**关键性质**：⑦ 回录后系统状态发生变化 → 回到 ① 首屏会看到这票的提醒。**loop 闭合。**

### 4.5 卖出提醒五层阈值

> 全部为**确定性阈值**，不含模型预测 —— 可解释 = 可信任 = 可自行复核。

| 层 | 触发条件 | 现成模块 | 改造量 | 是否 P0 |
|---|---|---|---|---|
| **L1 硬止损** | 成本价 × (1 − 5%)，无条件离场 | `stop_loss.py` 单票止损 | **现成**（接线） | ✅ P0-2 |
| **L2 趋势破位** | **有效跌破 MA5**（短线生命线，线上做多线下空）；辅以跌破 MA10/MA20 | `stop_loss.py` 组合止损 / `dynamic_stop.py` | **现成**（接线） | ✅ P0-2 |
| **L3 量能衰竭** | **炸板**（封单被砸开）/ 放量长上影 / 换手率 > 30% 且量增价跌 / 盘中脉冲爆量后快速萎缩 | ❌ **需新写行情事件钩子** | **新写** | ✅ P0-8 |
| **L4 指标死叉** | MACD 死叉、KDJ 高位死叉、RSI 超买回落 | `unified_risk.py` 三层风控 | **现成**（接线） | ✅ P0-2 |
| **L5 浮盈锁定** | **跟踪止损**：从持仓期最高价回撤 5% 触发，触发价**只升不降** | `dynamic_stop.py`（ATR + 支撑位） | **现成**（接线） | ✅ P0-2 |

**阈值默认值策略**（对齐竞品教训：通达信社区最常见误用 = "只设买入预警，不设风险预警"）：
- 用户回录持仓时**默认自动挂 L1 + L2 + L5**，用户可改可关，**默认开启**。
- L3（炸板）默认开启（打板场景退出信号，一等公民）。
- L4 默认开启但频率最低档（"每日一次"），避免指标类噪音。
- UI 引导文案固定为："**已自动为你挂了 N 条卖出提醒。多数人只设买入预警不设风险预警——卖出提醒才是保命的。**"

**跟踪止损的 T+1 特殊性**：A 股 T+1 下，当日买入不可卖出，因此**新买入持仓当日不应产生 L1 卖出提醒**（会给出不可执行的建议）。规则：**L1 仅在持仓次日起生效**；L2/L3/L4/L5 当日可生效但文案需标注"T+1 限制：当日买入不可卖出"。→ 列为待确认问题 Q3。

| 原则 | 具体要求 |
|---|---|
| **首屏回答"要处理的事"** | 打开系统的第一眼必须能回答"我手里这些票今天有什么事"。一切围绕"待处理项"组织，不围绕"信息量" |
| **输出与我的对象建立关联** | 任何列表型输出（候选、消息、指标）都要能回答"这条和我的持仓/自选有关吗"。无关联的输出对实盘用户是噪音（**P0-5 的设计根因**） |
| **可解释优先于聪明** | 每条提醒必须能展开"触发依据的具体数值/图形"。禁止只给一个综合分数或"AI 判断"字样（N4 的技术保障） |
| **默认开启，但可一键关** | 阈值自动挂载降低配置门槛（对抗"只设买入预警"反模式），但**任何阈值用户都能改能关**，且不隐藏开关位置 |
| **不打扰** | 提醒频率三档；同一条件重复触发按档位去重；连续忽略自动降频；非提醒区不产生红点 |
| **对象稳定性可见** | 今日候选的冻结状态、参数快照冻结日期、我的持仓更新时间**都要显式展示**——让用户看见"它没变"，而不是让用户猜 |
| **输入要顺手，输出要可核对** | 回录 ≤3 点击；每条输入都产生一个可见后果（回录→挂阈值→提醒），构成可归因的决策链 |
| **能力不隐藏，入口才收敛** | 砍的是导航位，不是数据。个股研究仍可通过深链到达（"/stock/:code"）。避免用户说"你把功能删了" |
| **移动使用降级** | v1 是 PC 工作台；盘中盲区在 P2-6，不在 v1 假装解决 |
| **一致性** | 术语全站统一：「我的持仓」「今日提醒」「今日候选」，禁止同物多名 |

### 7.2 数据模型（仅两处新增，其余复用）

```
# 新增 1：实盘卖出阈值配置（每条持仓 × 每条规则）
position_alert_rule
  id, position_id, level(L1|L2|L3|L4|L5), enabled(bool, 默认 true),
  param_value(%, 如 0.05), trigger_price(动态: L5 上移),
  freq_mode(once|daily|always, 默认 once),
  origin(AUTO_DEFAULT|MANUAL),            # AUTO_DEFAULT = 回录自动挂载

# 新增 2：提醒 / 告警事件（收件箱数据源）
alert_event
  id, level, symbol, position_id(nullable),

  basis_json{  # 触发依据，前端展开复核用

```
- `portfolio` 侧：**不新建持仓模型**，`backend/portfolio.py` 的 `add_holding` / `close_position` 直接复用。
- `snapshot` 侧：新增 `frozen_at`（冻结时刻）+ `incremental_json`（盘中增量）。
- **P0-5 侧：不新建表**。持仓/自选已有数据，排序在应用层完成；仅需在候选响应中附加 `hit_position` / `hit_watchlist` 两个布尔标记。

### 7.3 关键约束

1. **风控计算不能污染回测**：现有风控在回测路径中被调用，接实盘时需通过**独立入口**（新函数或显式 `mode=LIVE` 参数），避免实盘持仓进入回测统计、也避免回测时间轴污染实时阈值。
2. **性能**：盘中轮询 L1/L2/L4/L5 为轻量计算（价格 + MA + MACD），可挂在既有行情刷新节奏；**L3 需要事件订阅**，不能靠轮询（这是 P0-8 改造量高的原因）。
3. **迁移**：现有 `HoldingsPage` / `WatchlistPage` 数据源保留合并；`ConceptsPage` 是**纯派生只读投影**（无 localStorage、无 POST/PUT），其内容来自 `/api/catalyst`，**并入 `/stream` 是去重不是重写**；`groupEventsBySector`（`catalyst-client.ts:115`）是板块聚合的**唯一实现**，**务必复用、不要重写**（下线页面后 `/stream` 直接复用，函数不会死）；`/concepts` 下线时加 legacy redirect；`/stock/:code` 路由保留但从 NAV_LINES 移除。
4. **数据可信**：风控告警写入必须带 `basis_json`，**无依据的提醒不允许入库**——这是"可解释=可信任"的技术强制。
5. **端点与能力不被误删**（对应 N9）：本次改动范围限定在**前端路由与导航**，后端 63 端点零删除。CI 应加两条断言：
   - 端点数只增不减；
   - ⚠ **`src/aqsp/backtest` / `strategies` 的测试数只增不减**——**端点断言管不到 DSR/PBO/CSCV，它们是 Python 模块不是 HTTP 端点**。只断言端点数，仍可能把"砍界面"执行成"删能力"。

### 8.1 最终里程碑顺序

> ⚠ **v1 工期口径已作废**：v3 范围大于 v1（新增 P0-5、P1-1 扩为 5 个子项、P0-4 与 P0-5 均上调为中改造、P1-4 归位 M1），**v1（M0–M3）≈ 14.5–23 人日≈ 4–5.5 周日历（单人 ×1.2）**。

### 8.1.1 为什么 M1 是四条（界面收敛必须一次做完）

```
P0-5 → 候选区顶出"命中你持仓/自选"的项
P0-6 → 持仓+自选合并成一屏
P1-4 → 把过程数字从这两个页面上清掉
```
**三者合起来才构成一次干净的"界面收敛"**；拆开则用户要分两次经历"变干净"。而 v1 的整个叙事就是**一次把界面收拾干净**。

**代价（接受）**：M2 降为单条（P0-4，2–4 人日），成为最短里程碑。
**判断**：**M2 短不是问题，M2 拖着 P1-4 才是问题** —— 那会让 P0-4 的"冻结"叙事被"下架量化指标"稀释，而冻结恰恰是用户唯一主动点名的断裂。

⚠ **代价的连带影响**：P1-4 移入 M1 使 **TD-0 的截止时点从"M2 前"提前到"M1 的 P1-4 开工前"**，比原计划更紧。见 8.6 第 7 条。

### 8.2 M0 必须四件同批，不可拆（v2 关键修正，v3 保留）

> 初版把 P0-3 排进 M2 是**实质性缺陷**。缺陷链：
> ```
> 用户从未回录 → 持仓为空 → P0-2 无对象可跑 → 0 条提醒
> → P0-1 首页恒显「今日无触发」→ M0 交付了，但用户看到的是一个什么都不说的系统
> ```
> **这个缺陷在演示环境里看不出来**（手工塞几条持仓一切正常），属于"上线后第一周才发现、回滚也救不了信任"的类型。
>
> **M0 = P0-3 + P0-2 + P0-7 + P0-1，四者严格同批上线**，缺任一项价值主张都不成立：**无输入 / 无阈值 / 无提醒 / 无出口**。

### 8.3 排序原则：主动需求 vs 被动需求（v2 确立，v3 保留）

| | 候选冻结（P0-4 / M2） | 卖出提醒（M0） |
|---|---|---|
| 需求性质 | **被动**——用户不特意去看候选，冻结与否不影响他交易 | **主动**——系统不主动说话，用户就没有理由打开系统 |
| 缺失后果 | 首页候选区内容不可信（负资产） | **用户不打开系统 ⇒ 其余全部里程碑无真实用户可验证** |
| 可否部分补偿 | 可（降级为二级页 + 显式提示） | 不可（没提醒 = 没产品） |

**核心论证：M0 是 M1–M4 的验证前提，不是"优先级高"。** M1 的"分组排序"要靠真实持仓才有内容；M2 的"量化下线"要靠用户真的进候选页才有意义；M3 的"提醒回写"要靠真实触发才有对象。**在 M0 之前交付它们，等于交付一个没有用户的产品的下半部分。**

### 8.4 为什么 M2（候选日内稳定）排在 M3（处置闭环）之前

| | P0-4 候选冻结 + P1-4 量化下线 | P1-3 + P1-2 处置闭环 |
|---|---|---|
| 缺失时的性质 | **不可用**：候选每天换一批；用户明说"早中午进去都是一批新的内容"——**用户唯一主动点名的断裂** | **可绕过**：提醒照样响，用户可去持仓页手动平仓，只是多一步 |
| 兑现的是什么 | **承诺兑现**：系统前后一致 = "稳" | **体验完整**：loop ⑦ 闭合 = "顺" |
| 是否阻塞下一步 | 是：不冻结就没法放心把候选区放首屏 | 否：M4 炸板钩子不依赖它 |

**排序原则：先让用户能依赖，再让用户省事。**

### 8.5 ⚠ P0-5 与 P0-4 必须相邻交付（v3 新增，只在 v2 之后才成立的约束）

> 这是本文档最重要的一条排期硬约束，且**它只有在 P0-5 存在之后才成立**——初版（v1）没有 P0-5，因此给不出这个论证。

初版主张"冻结可以后置"，前提是"候选一直是推荐榜"——用户本就把它当噪音，稳定性差一点无伤大雅。**但 P0-5 上线后，首屏变成了"命中你持仓/自选的前 5 只"，性质完全变了**：

```
09:15  P0-5 上线 → 系统把"命中你持仓"的 2 只顶到第 1、2 位，打上「持仓」标签
              ↓ 用户据此定下今日计划（这正是 P0-5 的设计目的）
11:00  整批重算 → 这 2 只掉出列表，或被陌生票挤下去
14:00  再看 → 又是另一批
```

⇒ **P0-5 无 P0-4，会制造一个 v2 之前不存在的失败模式：系统先明确承诺"这几只是你的票"，然后把它们撤回。**

**这比"候选一直是榜单"更伤信任**——它从"无承诺"变成了**主动失信**。用户可以接受系统说不上话，不能接受系统说了又改口。

**⇒ 硬约束：P0-5（M1）与 P0-4（M2）必须相邻交付，不可隔着任意里程碑。**
- 本方案：P0-5 在 M1、P0-4 在 M2 ⇒ **已满足**。
- 若排期需要把 P0-4 后推，**必须**同时把 P0-5 一起后推（两者绑定为一个不可拆的交付单元），**绝不允许 P0-5 单独先上**。
- 若工期实在压不住，**备选降级方案**：P0-5 先上，但命中的候选**强制附上生成时间戳**（"09:15 快照"字样），把"承诺"降级为"带时间戳的快照"，避免用户误以为是实时结论。此为降级，非首选。

### 8.6 排期约束与风险提醒

1. **P0-3 与 P0-7 不可拆**：P0-7 的实现方式就是"挂在 P0-3 的提交回调上"，无 P0-3 则物理上无法完成（详见 8.2）。
2. **P0-4 不可无限后置**：若工期紧张需砍，**必须同时**把今日候选降级为二级页 + 加显式提示"候选每日重算，盘中可能变化"，并把"日内候选集合稳定性"从成功指标中**撤下**而非留着做不到。
3. **不建议砍 P1-4**（量化指标下线）：≤1 人日，感知收益最高，直击"纯粹为了做而作"。
4. **不要砍 P0-3**：砍它 = 砍掉 M0 的数据前提 = M0 空转。
5. **唯一工期变量是 P0-8**（唯一新写，须事件驱动）。🔴 **移出 v1 ≠ 搁置**：M4 期间仍需**并行推进数据源可得性调研**——它决定 L3 是"事件订阅（封单/逐笔）"还是"降级为分钟线形态判定"，是**唯一不可边做边定的项**。**调研可以早，开工可以晚；调研若搁置，v1.1 排期时要从零开始。** 若工期紧张需砍 P0-4，同样**必须把今日候选降级为二级页 + 加显式提示"候选每日重算，盘中可能变化"**，并把"日内候选集合稳定性"从成功指标中**撤下**而非留着做不到。
6. **M0 上线首周盯噪音率**（忽略+未处理 > 40% 立即降灵敏度）。缓解措施：`should_send_notification` 去重兜底 + `freq_mode` 字段按三档语义**在 M0 就建好**（控件延到 P1-2 上）——字段先建、控件后上，避免二次迁移。**提醒"太吵"的风险在 M0 首周就已存在，不能等 P1-2 上线才防。**
7. ⚠ **TD-0 必须在 M1 的 P1-4 开工前完成**（v3 升级，P1-4 归位 M1 后时点再收紧）：P1-4 要把 7 维权重"固化为冻结快照并在前端展示"，这正是让 `composite.py::calculate_detailed_scores` **首次进入生产展示路径**——而它在当前生产配置下**返回值就是错的**（`thresholds.yaml:13` `price_volume_corr_weight: 0.3` + `:77 enabled: true`，pvc 是当前生产唯一启用的第二维度，恰在明细版缺失的 5 个维度里）。⇒ **交付给用户看的那份"依据"是错的。** 一个不可信的解释比没有解释更伤信任，且直接违背本文 N4（可解释）与"无依据不允许入库"两条原则。TD-0 仅 1–2 人日，可并行于 M0/M1。**顺带清理 `amount_ratio` 僵尸维度（见 P2-9：权重恒 0、打分从不调用、删除不改变任何选股结果，但留着会让下一个读代码的人以为它生效）。**
     ⚠ **TD-0 完成后须校验一条不变量**：`CompositeStrategy.__init__` 中**不应再存在任何"已实例化但 `calculate_score` 从不调用"的策略对象** —— 这是把 `amount_ratio` 从个案升级为可复检的不变量，防止后续新增维度重犯。
8. **数据源与租户一致性（v3.3 降级改写）**：
   - ✅ **原风险"平行账本"已被推翻**：`/api/portfolio` 与 `backend/portfolio.py` 是同一份数据（全文只有一个写盘路径 `_pf_file()` → `<tenant_dir>/portfolio.json`，`_LOCK` + `os.replace` 原子写，无中间存储层）。**P0-3 写入与 P0-6 读取是同一份，L1 成本价不会被分叉。**
   - 🟠 **风险等级下调：高危信任崩塌 → 中危数据陈旧**（v3.3 据代码核实降级）。此前把"6 份 portfolio.json 并存"读作"静默分叉已发生 5 次"，**该解读错误**：
     - `_maybe_migrate_to_tenant()`（`portfolio.py:85-100`）是**设计内迁移**：非 local 租户首次访问时，若自身为空且 local legacy 持仓存在，则 `shutil.copy2` 复制过来（注释原文："让从单用户升级到多用户的老数据无缝落到主人自己的租户桶"），并用 `_MIGRATED_TENANTS` 保证每租户只迁一次。
     - ⇒ **磁盘上那 6 份文件是同一份 local 真身被复制 5 次，不是 5 份独立数据**；且因都为空故从未分叉出实质差异。
     - ⇒ **真实风险是"数据陈旧"而非"信任崩塌"**：切到新租户时读到的是**迁移快照**而非最新状态，用户可能看到"持仓少了最近一笔"，但**L1 成本价不会算错**（各租户文件内容一致）。表现为**可察觉的数据不一致**，而非静默的阈值失真。
   - 🟠 **保留的硬约束（仍有效，但性质是"防止引入"而非"修复既存"）**：
     - **硬约束**：新增 portfolio 写入必须走 `api.addHolding` / `api.closePosition`，**不得新写 `fetch`**。实测现有 3 处 `fetch` 已全部经 `authHeaders()`、无裸 fetch 存量（`api.ts:95/132`、`catalyst-client.ts:46`）⇒ 本项性质是"**别在 P0-3 引入**"，省掉 0.5–1 人日的全前端扫描。
     - **验收**：**隐私模式下录入持仓，刷新后仍在**。
   - ⚠ **仍需注意的边界缺陷**：`api.ts:130` 判 `if (Object.keys(headers).length > 0)`，而 `authHeaders()` 在 localStorage 不可用时返回 `""` ⇒ `Object.keys("").length === 0` ⇒ **请求头被整个丢弃，落 `local` 租户**。**隐私模式 + 未设 API Key 时今天就已经是裸请求**（磁盘最近活动正是 local 租户，时间线吻合）。
     ⇒ **隐私模式与"演示重置"是同一链路的两个入口**：前者走 `authHeaders()` 退化，后者走手动清库，两者都会让用户读到旧数据。
   - ⚠ **冷启动演练仍需从真实空库起步，但理由需修正**：**主因是"不能预置持仓"**（否则掩盖 M0 空转）；"误读为持仓丢失"是**次要**理由，且其成因是**迁移快照陈旧**而非读错目录。**两个缺陷仍会叠加在同一句话的表象上**（"我的持仓不见了"），不隔离仍会互相掩盖。
   - ✅ **无迁移包袱**：实测真实持仓存量 = 0（6 份文件全空）⇒ P0-3 是纯新建，不需要数据迁移步骤。
9. ⚠ **CI 断言需补一半**：端点断言**管不到** DSR/PBO/CSCV——它们是 Python 模块不是 HTTP 端点。除"端点数只增不减"外，须同时断言 **`src/aqsp/backtest` / `strategies` 的测试数只增不减**，否则"砍界面"仍可能被执行成"删能力"（对应 N9）。

## 附录 B：核心结论速览（给老大的一页纸）

1. **一句话**：把首页从"今日推荐榜"改成"今日提醒收件箱"，让系统中心对象从"今天有什么票"换成"**我手里这些票今天有什么事**"。
2. **三步走**：① 持仓+自选合并成唯一持久层；② 把 `stop_loss` / `dynamic_stop` / `unified_risk` 从回测里拔出来接到这个持久层，产出 L1/L2/L4/L5 确定性卖出提醒；③ 给一条"我操作了"的轻输入，让提醒自动带上默认阈值。
3. **新增第四条**：**候选区要"命中我的持仓/自选"优先**。用户优先级 ②（选股+大盘→买卖建议）的卡点不是缺页面，是 `/today` 只按策略分组、候选和我的持仓没建立关联。这是**纯排序改造，成本最低、感知最强**。
4. **今天的候选不再是主角**——它是提醒的来源之一（"你的自选里有 2 只命中今日候选"），而不是首页主体。
5. **砍得动的原因**：63 端点前端只用 21 个，31 个单票端点零调用，ConceptsPage/StockResearchPage 是孤儿路由且前者与 `/stream` 同源同内容。**砍的是入口不是能力**——7 项导航收敛到 4 项，零能力损失。
6. **成本优势**：P0 八条里 **6 条是接线/排序**（零件已存在，只是接错对象），1 条轻 UI，1 条新写（炸板钩子）。**不新增选股能力、不新建持仓数据模型**（只加 2 张表：阈值配置 + 提醒事件）。
7. **要老大拍板 8 个问题**（见第九章）。最关键三个：**Q3**（T+1 下当日买入的止损提醒是否给）、**Q5**（盘中提醒要不要外发推送）、**Q6**（炸板钩子是否必须在 v1）。
