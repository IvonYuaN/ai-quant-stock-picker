## 二、PRD v2 的三处内部矛盾（须先修正再开工）

> 以下三处不是路线图与 PRD 的分歧，而是 **PRD v2 内部的自相矛盾**。前两处若不修正，会直接导致排期不可执行。

### 矛盾 1 🔴 M0 的 P0-7 依赖 M2 的 P0-3（依赖倒置）

| 出处 | 原文 |
|---|---|
| PRD 第 195 行（P0-7 依赖栏） | P0-7 回录即自动挂阈值 …… **"挂在 P0-3 的提交回调上"**（第 413 行 M0 范围亦重申此点） |
| PRD 第 413 行（M0 范围） | M0 = **P0-2 + P0-7** + P0-1 |
| PRD 第 415 行（M2 范围） | M2 = **P0-3** + P1-3 + P1-2 |

**推论：** M0 里有一条需求的依赖落在 M2。P0-7 的实现方式（挂在提交回调上）决定了它**在 P0-3 之前物理上无法完成**。

**修复方案（唯一，且不改变 M0 的需求集合）：把 P0-3 从 M2 提到 M0。**
M0 变为 `P0-3 + P0-2 + P0-7 + P0-1`，析客草案的其余三条原样保留。

**为什么这条不只是形式问题：** 用户从未回录 ⇒ 持仓为空 ⇒ P0-2 无对象可跑 ⇒ 0 条提醒 ⇒ P0-1 首屏恒显"今日无触发"。**M0 交付了一个什么都不说的系统，而这个缺陷在演示环境里看不出来**（手工塞几条持仓一切正常）。

### 矛盾 2 🟠 P0-5 的依赖被高估

| 出处 | 原文 |
|---|---|
| PRD 第 193 行（P0-5 依赖栏） | **"依赖 P0-6 的持仓/自选合并结果"** |
| PRD 第 368 行（7.1 复用栏） | P0-5 复用 **"持仓/自选集合（`backend/portfolio.py` + 自选数据源）；`screen_universe` 输出不变"** —— **均现成** |

**推论：** P0-5 需要的是**持仓/自选数据**（现成），不是**P0-6 的页面合并**。PRD 自己三处都写明了这一点，但依赖栏仍写"依赖 P0-6"。

### 3.1 对析客逆直觉主张的判断（他要求"当面讨论"）

> **我的结论：同意"M0/M1 优先于冻结"，但反对把冻结放到第 4 位——要求 P0-4 提前到第 3 位，与 P0-5 相邻。**

**✅ 我同意的部分：冻结确实不该排最前。** 理由比他给的更硬——这不是偏好排序，是拓扑依赖：

| | P0-4 候选冻结 | M0 提醒闭环 |
|---|---|---|
| 需求性质 | **被动**：用户不特意去看候选，冻结与否不影响他交易 | **主动**：系统不主动说话，用户就没有理由打开系统 |
| 缺失后果 | 首页候选区内容不可信（负资产） | **用户不打开系统 ⇒ 其余里程碑无真实用户可验证** |

**M0 是 M1–M4 的验证前提**：M1 的分组排序要靠真实持仓才有内容；M3 的处置回写要靠真实触发才有对象；P0-5 的"命中优先"要靠真实候选与持仓重叠才有意义。**在 M0 之前交付它们，等于交付一个没有用户的产品的下半部分。**

**❌ 我不同意第 4 位的部分：v2 新增的 P0-5 把冻结从"可以后置"变成了"必须紧邻"。**

析客 v1 的逆直觉论证建立在"候选仍是推荐榜"这个前提上。**但 v2 加了 P0-5之后，首屏第二屏变成了"命中你持仓/自选的前 5 只"**（成功指标：命中项出现在前 5 位的比例 = 100%）。这意味着：

```
09:15  P0-5 上线 → 系统把"命中你持仓"的 2 只顶到第 1、2 位，并打上「持仓」标签
              ↓ 用户据此定下今日计划（这正是 P0-5 的设计目的）
11:00  整批重算 → 这 2 只掉出列表，或被新的陌生票挤下去
14:00  再看→ 列表又是另一批
```

**⇒ P0-5 无 P0-4，会制造一个 v1 之前不存在的失败模式：系统先明确承诺"这几只是你的票"，然后把它们撤回。** 这比"候选一直是榜单"更伤信任——因为它从"无承诺"变成了"承诺后撤回"，是**主动失信**。

**⇒ 结论：P0-5 与 P0-4 必须相邻。** P0-5 在 M1，P0-4 必须在 M2（紧邻），不能隔着 M3。

**这个论证 v1 给不出来**——它依赖 P0-5 这个 v2 才有的需求。**建议连同本节一起转给老大。**

#### 🔴 真正的风险：租户目录随请求头切换（数据析新发现，我已复核）

链路里确实藏了一层，就是"中间存储层"的近亲——**租户目录**：


**文件路径由请求头决定**（我已复核 `tenant.py:29-36` 与 `portfolio.py:39-44`，确认优先级为 `X-User-Id > API Key 哈希 > local`）。前端 `api.ts:79-88` 的 `authHeaders()` 会带 `X-User-Id`（来自 `loadUserId()`，localStorage key `vr-user-id`，**首次访问生成 UUID 后固化复用**，`api.ts:65-77`）。

1. **P0-3 回录入口与 P0-6/P0-5 读取必须走同一个 `authHeaders()`** —— 若一个用 `api.*`（自动带头）、另一个用裸 `fetch`（不带头），会落到不同租户目录。**这才是"静默分叉"的真实形态。**

3. 演示环境那条提醒的机制不是"表分叉"，是"**目录随header 变**" ⇒ 演示环境重置必须连`vr-user-id` 一起重置，否则会看到"上一轮录的持仓不见了"。

### 6.2 🆕 Q6 改判：P0-8 移出 v1（析客 v3 已正式改判，采纳）

**析客已正式改判 P0-8 移出 v1**，理由与我一致但更完整：**"唯一需新写 + 数据源可得性未验证"的 5–8 人日需求放在 v1 尾部，风险是它会成为唯一拖期项，且拖的不是它自己而是整个 v1 的收尾。**

### 6.3 砍的判据

用户原话痛点排序：①"早中午都是一批新的内容"（P0-4）②"该卖的时候你得提醒我"（P0-2/7/1）③"我实盘处理完输入一点信息"（P0-3/P1-3）④"板块太多余，持仓自选合并就够"（P0-6/P1-1）⑤"候选看不出命中我哪几只"（P0-5）

### 6.4 砍 P0-4 的强制配套条件（不可只砍不做）

若采用 v1-min，**必须同时**：

1. **今日候选从首屏降级为二级页**（不放首页模块顺序）；
2. **候选页顶部显式提示**："候选每日重算，盘中可能变化，请勿作为盘中决策依据"；
3. **从成功指标撤下"日内候选集合稳定性"**（不是保留一个做不到的指标——留着就是自设失败）；
4. **同步撤下或改写"命中持仓/自选出现在前 5 位比例 = 100%"**（P0-5 会因列表重算而失效）；
5. **诚实告知老大**：这是**已知未解决项**，不是"已修"。


### 6.5 明确判断

**不推荐砍 P0-4。** 它只需 2–4 人日（不到 v1 全周期的 1/5），却是用户唯一主动点名的断裂，且在 P0-5 之后不做会**主动制造失信**。

**P0-8 已按 Q6 改判移出 v1（见 §6.2）**，理由与上条同源：唯一新写项 + 数据源未验证，是唯一会拖住整个 v1 收尾的因素。

**明确不建议砍**：**P0-5**（析客与我一致，用户优先级 ② 的唯一卡点）、**P0-3**（砍它 = 砍掉 M0）、**P1-4**（≤1 人日，感知收益最高，且是"上线时"硬指标）、**P1-1**（用户明说"板块太多余"）。

### 8.2 三处修正（相对初步排查报告）

| # | 报告 | 核实结论 |
|---|---|---|
| 1 | 主打分 11 维 | **12 维**（报告列举项本身即 12 项，计数笔误） |

| 3 | "属潜伏缺陷" | **当前生产配置下已生效** |

### 8.3 为何严重性高于"潜伏"（关键）

`config/thresholds.yaml:13` `price_volume_corr_weight: 0.3` + `:77 price_volume_corr.enabled: true`
⇒ **pvc 是当前生产唯一启用的第二维度（与 momentum 0.3 平分总分），而它恰在缺失之列。**

```
calculate_score(...)      = momentum×0.3 + pvc×0.3   （归一化）
calculate_detailed_scores = momentum×0.3             （w_sum 只含 7 维）
                          ⇒ detailed["total"] ≠ calculate_score()
```

**今天调用明细版就会拿到与选股结果不一致的分数。**

**CI 结构性盲区（比缺维度本身更值得修）**：`tests/test_strategies.py:375` 正好守着 `assert detailed["total"] == approx(half_score)`，但**该测试用 `Thresholds()`（dataclass 默认，5 个缺失维度权重全 0 ⇒ 两版恰好相等）而非 `load_thresholds()`（生产 yaml）** ⇒ **CI 跑绿也抓不到。** 需警惕同类"默认与生产不一致"的缺陷在该文件里可能还有其他。

### 8.4 🆕 v2 使其紧迫性上升：必须先于 P1-4

P1-4 要把 7 维权重结果"固化为冻结快照并在前端展示"——**这正是让 `calculate_detailed_scores` 首次进入生产展示路径的需求。而它当前返回错误数值。**

**⇒ 交付给用户看的那份"依据"是错的。** 且这直接违背 PRD 的核心原则（6.x"可解释优先于聪明"、7.4"无依据的提醒不允许入库"）——**一个不可信的解释比没有解释更伤信任**。

**⇒ TD-0 必须先于 P1-4 完成。** 排期上：TD-0（1–2 人日）可并行于 M0，但**在 M1 的 P1-4 开工前必须完成**（P1-4 现已移入 M1，见 §4）。

### 8.5 修法（单一事实源）

抽出 `_collect_dimension_scores(data)` 与 `_resolve_weights(regime)`，两函数共用；`calculate_score` = `_assemble_total(...)`；`calculate_detailed_scores` = 同一份`_assemble_total` + 各维度分写入明细。**不变量：`detailed[s]["total"] ≡ calculate_score(...)[s]`。**

**一并修三处一致性**
| # | 位置 | 问题 | 修法 |
|---|---|---|---|
| a | `composite.py:168-172` | `amount_ratio` 策略已实例化、权重函数已实现，但主版从未调用 ⇒ 僵尸维度 | **建议删除**实例与 `_has_amount_ratio`/`amount_ratio_weight_for`（`amount_ratio_weight` 默认 0.0，删除**不改变任何选股结果**，安全方向） |
| b | `composite.py:488` | `vsurge_scores.get(symbol, 0.0)` —— 12 维中**唯一用 0.0 兜底**（其余均 0.5 中性） | 统一为 0.5。当前权重 0 无影响，但启用后缺失标的会被判最差而非中性 |
| c | 测试阈值来源 | 见 8.3 | 新增用 `load_thresholds()`（生产 yaml）的测试 |

**验收测试（缺一不可）**
```python
def test_detailed_dimension_set_equals_main():
    """明细版维度集 == 主版维度集"""
    assert detail_dims == main_dims
```
