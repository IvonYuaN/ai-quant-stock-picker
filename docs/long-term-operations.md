# 长期运行与研究闭环

本项目长期目标不是只让代码通过，而是持续维护一条可审计的“研究 → 开发 → 发布 → 前端验证 → 复盘”闭环。系统仍然只提供候选、纸面验证和研究证据，不自动下单。

## 五条工作线

| 工作线 | 必须持续回答的问题 | 主要证据 |
| --- | --- | --- |
| 研究 | 新策略是否有经济假设、样本门槛和 walk-forward 证据？ | `docs/short-term-realtime-roadmap.md`、walk-forward gate |
| 开发 | 改动是否可复现、类型正确、没有未来数据？ | pytest、ruff、变更说明 |
| 部署 | 运行的是否是已发布 commit，而非服务器脏 checkout？ | release provenance、调度审计、部署闭环 |
| 前端 | 用户看到的是当前、足够新鲜且不误导的结果吗？ | React build、API contract、隔离无头入口检查 |
| GitHub | 代码归档和手工验证入口是否可用？ | 手动 Actions、secret scan |

## 固定节奏

- 每次改动：定向测试、前端 build、secret scan；影响运行效果时补服务器 health、数据新鲜度和关键页面检查。
- 每周：公开 API `/api/health`、首页和 `/variants` 入口、调度与 release provenance；GitHub 只在需要时手动验证，不作为线上门禁。
- 每月：walk-forward / DSR / PBO 证据、阈值版本冻结状态、数据源成功率、通知噪音和前端信息架构复盘。
- 每季度：重新审视研究边界、数据源替换、部署回滚路径和用户可见措辞；不因短期收益直接调参。

GitHub Actions 保留为手动验证入口，不再自动触发 CI、Dependabot 或周期邮件；线上是否成功只以服务器不可变 release、调度、数据新鲜度、API health 和用户可见结果为准。Codex 的长期 heartbeat 负责带着同一目标回到当前任务并处理失败项。任一服务器检查失败，只能报告为“未验收”或“阻塞”，不得描述为已上线。

## 处理顺序

1. 先确认失败属于研究证据、代码、数据、部署、前端还是 GitHub 工作流。
2. 在仓库内建立最小可复现修复和测试；服务器只读诊断，除非存在明确的安全、可用性或数据完整性重大风险。
3. 按部署闭环重新验证：发布来源、调度、health、数据新鲜度、前端入口和关键结果。
4. 把重复出现的故障沉淀为测试、脚本、规则或文档，避免依靠人工记忆。
