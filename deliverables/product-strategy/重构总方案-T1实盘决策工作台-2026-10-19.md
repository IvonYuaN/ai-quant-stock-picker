## 📌 TL;DR

- 🔴 **两条设计准则（贯穿全文，优先于任何单条需求）**：
  1. **「承诺后撤回」比「从未承诺」更伤信任** —— 你能接受系统说不上话，不能接受系统说了又改口。
  2. **让系统看起来具备某能力，比明确承认不具备更危险** —— 前者让你误以为被保护，后者至少让你知道缺什么。
     两者同源于"**失效不报错**"，因此所有范围调整都必须回查牵连面。
- **中心对象换人**：首屏从「今日推荐榜」改为「**今日提醒收件箱**」——从"今天有什么票"变成"**我手里这些票今天有什么事**"。这一条决定其余所有改动。
- **缺的从来不是能力，是接线**：风控引擎（`stop_loss.py`/`dynamic_stop.py`/`unified_risk.py`）全现成，只是接在回测上没接实盘持仓；候选冻结的 `save/load_snapshot` 也现成，只差一道当日闸门。**P0 八条里 6 条是接线/排序。**
- **三处硬阻塞待老大拍板**：提醒通道站内 vs 外发（唯一影响架构）、T+1 当日止损规则、实盘/观察仓。
- **一个现在就是错的技术债（TD-0）**：明细版打分与主版口径不一致，且**当前生产配置下已生效**（pvc 是生产第二维度），CI 因用 dataclass 默认阈值而抓不到。**须先于 P1-4 完成**。

## 一、根因（为什么"逻辑很乱"）

**系统站错了立场**：一直按"研究员每天给你换一批候选"设计，而你实际是 **T+1 实盘**用户，需要"围绕我手里这批票做处置决策"。

**行业证据（竞析，6 个对标）**：富途/通达信/雪球**甚至开源 Qlib**，首页中心对象全是"我的持仓/自选"，**没有一个是"今日推荐"**（Qlib 产物就是"目标持仓"）。信任四属性——对象稳定/输入可控/输出可执行/不打扰——本系统**四条全违约** ⇒ "早中晚不一样"是**机制性失败**，不是内容质量问题。

**"为做而作"被量化（数析）**：后端 63 端点，前端只调 21，**31 个单票端点零调用**（龙虎榜/解禁/两融/资金流…是研究员底座）。DSR/PBO/CSCV/7 维权重——**用户从不消费**。

### 🔴 排期硬约束：P0-5 ↔ P0-4 相邻交付（不可拆）

```
09:15  P0-5 上线 → 把"命中你持仓"的 2 只顶到第 1、2 位，打「持仓」标签
              ↓ 用户据此定下今日计划（这正是 P0-5 的设计目的）
11:00  整批重算 → 这 2 只掉出列表，或被陌生票挤下去
14:00  再看 → 又是另一批
```
⇒ **从"无承诺"变成"主动失信"。** 用户可以接受系统说不上话，不能接受系统说了又改口。
**降级方案**：工期压不住时，命中的候选**强制附 09:15 时间戳**，把"承诺"降级为"带时间戳的快照"。

### ⚠️ P0-5 验收必须二分（否则会误判返工）

🔴 原验收写"命中候选大量出现在末位 ⇒ 重叠度低"——**因果链是错的**：
P0-5 的作用就是把它们顶上去，**"出现在末位"只可能说明排序没生效**，绝不可能说明重叠度低。
后果：一旦真实重叠度低，团队会误以为 P0-5 没做对而返工，把时间花在修一个没坏的排序上。

**拆成两条互不干扰的判定**：
- **排序生效性** → 用**构造数据**验收（20 只含 2 持仓 + 3 自选 ⇒ 必须在前 5 位），**不依赖真实重叠度**
- **重叠度健康度** → 单列"命中总数"观测，**< 3 时启动 P2-8**（候选池筛选口径调整）

### P0-8 移出 v1 的处理（析客改判，采纳）

**理由**：它是唯一需新写、且**数据源可得性尚未核实**的需求（5–8 人日）。放 v1 尾部会成为唯一拖期项，
且拖的不是它自己而是**整个 v1 的收尾**——用一个未核实的数据源赌收尾不划算。

**配套（第一准则的落地）**：v1 呈现为 **L1/L2/L4/L5 四层，L3 在 UI 上显式标注"待上线"**，
**不得隐藏**——隐藏就是典型的"承诺五层、交付四层"，等于又制造一次承诺与实际不符。

**⚠️ 移出 v1 ≠ 搁置调研**：M2 期间仍须**并行推进数据源可得性调研**——
它是**唯一不可边做边定的项**（能否拿到封单/逐笔数据，决定 L3 是"事件订阅"还是"降级为分钟线形态判定"）。
**调研可以早，开工可以晚。**

### 🔴 两条设计准则（析客提议提级，覆盖面比"承诺后撤回"更广）

**准则一：「承诺后撤回」比「从未承诺」更伤信任。**

**准则二：让系统看起来具备某能力，比明确承认不具备更危险。**
前者让你误以为被保护；后者至少让你知道缺什么。**两者的共同点是"失效不报错"。**

三条已落地处（同一错误的不同变体，且**都不产生任何报错**）：
1. **P0-8 移出 v1** → L3 必须显式标注"待上线"，**不得隐藏**（隐藏 = 承诺五层、交付四层）
2. **`amount_ratio` 僵尸维度** → 留着会让下一个读代码的人以为它生效了（**文档债比技术债更贵**）
3. **TD-0 必须先于 P1-4** → 否则是"展示了一份错的依据"

⇒ **所有范围调整（删/挪/后置）都必须回查牵连面，不是往前看需求清单。**
（`amount_ratio` 是靠"列需求"这种方式永远发现不了的——只有真正核实"这个维度到底通不通"才会碰到。）

### 🔴 P0-4 跨日闸门重启失败（路线图 v2 实证，此前未被列出）

> 现象：P0-4 已上线且当日冻结生效，但**次日 09:30 盘中重跑时闸门判定"今日已冻结"而整批跳过重算** ⇒ 首屏显示昨日快照（数据停留在 T-1，且带"昨日快照"提示角标）。
> 性质：**闸门重启条件错误**（自然日 vs 交易日历），非算法缺陷。
> 根因：设计文档/实现把"当日"默认按自然日处理，忽略 A 股节假日无数据导致"最后一次运行日期"滞留。
> 处置：闸门的"当日已冻结"判定**必须以交易日历为准**（复用 `src/aqsp/data/trading_holidays.py` / `szse_calendar.py` 现有交易日历，非工作日回退），否则直接列为 M3 验收阻断项。

### 🔴 ④-b 租户目录（成因已查明 · **性质分两段**）

**成因（比原判断更精确）**：`authHeaders()` 只要**任一**头存在就注入（`api.ts:79-88`），
**不存在"两个都没有 ⇒ 裸 fetch"这条路径**。5 个 `u_` 桶是**曾经带过 `X-User-Id` 或 `Authorization`** 的真实租户。
而 7-21 有 5 份**同秒同内容**（10 bytes、10 段持仓代码）⇒ **同一会话内的缓存震荡**
（同一浏览器 profile 被并发开多个标签/实例，各自固化过不同 UUID）。
9-23 的 local 桶**时间上晚于** `authHeaders` 加持久的日期 ⇒ **最近活动已收敛到 local**。

**⇒ 风险性质分两段**：
- **7-21 震荡期 = 已发生·已自愈**（时间线收敛，不追）
- **机制未加护栏 = 仍潜伏**：将来再有一次 id 变化即复现

**🔴 真隐患在守卫的"可夹带"语义**（`portfolio.py:85-99` `_maybe_migrate_to_tenant`）：
```
新租户首次访问 → 若自身为空且 local 旧持仓存在 → 把 local 的持仓复制过来
```
主人首次用新版 Web（换了浏览器 id）⇒ **凭空多出 5 只持仓**
⇒ **可能把主人自己的组合复制进错误租户目录**（若 local 桶含他人数据 = 跨租户夹带）。
**危险等级：高于④-b 原风险。**

**⇒ ④-b 定为「中危 · 已发生 · 已自愈」**（不是高危信任崩塌）。
**依据修正（主理人 md5 实测）**：6 份文件 **md5 并不相同**，差异仅来自 `last_refresh`
（local = `2026-09-23 13:16`，5 个 u_ 桶全部 = `2026-07-21 14:16`）；
**`holdings` 确实全为 `[]`，从未造成数据分叉** ⇒ 原判断方向正确，依据表述按实测改写。

### 🟠 ④-d 跨租户副本陈旧（中危 · **已被上述 md5 差异实证**）

local 已更新到 9-23，5 个租户桶仍停在 **7-21 的旧快照、永不跟随**（守卫「已存在就不覆盖」）
⇒ **M0 录真实持仓后立即成立**：A 浏览器录的持仓，B 浏览器看到的是过期副本。
**当前 local 为空所以完全无害** —— 这是「无害与已埋雷并存」，不是「不存在」。

**验收（比「清空 vr-user-id 后为空」更贴近真实风险）**：
> **用无痕窗口（新 `vr-user-id`）打开，确认新租户为空、不会看到 local 的持仓**
> —— 那条测同租户持久化，**这条测跨租户数据泄漏**。

旧链接会落到"我的持仓"而非空页 ⇒ 用户此前**可能已在不存在的页面操作过**。

**验收（防止误判为"持仓丢了"——两条缺陷表象相同，不隔离会互相掩盖）**：
1. **local 桶已有持仓时，新租户首次访问必须为空**
